# RBAC 与人员能力主数据中心改造方案

## 0. 最终实施口径（优先级最高）

本节是 2026-08-17 确认的最终口径，覆盖本文后续章节中曾经提出的“双轨、兼容读取、数据源开关和分阶段回退”安排：

- 系统运行时只使用新 RBAC，不再读取 `users.role`、`users.permissions`、`users.allowed_tabs` 决定菜单、按钮或接口权限。
- 人员与能力主数据是账户管理、信息传达和维修管控的唯一人员来源，不再提供“启用人员主数据”开关。
- 新增和编辑账户必须关联有效人员，并在同一事务中保存账户状态、RBAC 角色和数据范围；至少一个角色、至少一个数据范围。
- 原有账户均视为测试账户，可在一次性迁移中清除；账户清除不级联删除信息接收人、阅读回执、维修记录和审计日志等业务历史快照。
- 唯一超级账号的工号、账号和内部 ID 均为 `54002010`，姓名固定为“赵威”。该账号拥有全部有效权限和全部数据范围，禁止编辑身份、角色、范围、状态，禁止停用、删除或由管理员重置密码，只允许本人登录后修改密码。全部人员工号统一为8位数字。
- 工时统计与考勤管理保留一级页面和独立权限组；业务功能未落地前只显示“功能建设中”，不显示模拟数据。
- 旧账户接口返回已移除状态；正式账户接口统一为 `/api/admin/accounts`，批量开户为 `/api/admin/accounts/bulk-open`。
- 本文后续凡出现“新旧双轨”“兼容旧角色”“恢复旧数据源”“逐步切换”等描述，均仅作为历史讨论记录，不再作为实施要求。

## 1. 改造目标

将当前“登录账户同时充当人员名单”的模型改造成以下四层：

1. **人员与能力主数据中心**：统一管理人员基本信息、组织、执照、授权和培训。
2. **登录账户体系**：账户按 `person_id` 关联人员，人员可以没有登录账户。
3. **标准 RBAC**：角色、权限、账户角色关系独立建模，一个账户可拥有多个角色。
4. **数据范围与业务资格策略**：RBAC 决定能否操作系统；人员执照、授权、培训状态决定能否承担具体任务。

人员与能力主数据中心在“系统设置”中作为独立二级页签提供管理界面。账户管理、车间人员安排、信息传达、维修派工、工时统计等模块通过统一后端服务读取人员数据，不再各自维护人员名单。

## 2. 当前模型与主要问题

当前系统存在以下结构：

- `users` 同时保存登录账户、人员姓名、组织班组和人员职能。
- 角色仅有 `receiver`、`publisher`、`admin`，角色定义硬编码在服务端。
- `permissions`、`allowed_tabs` 作为 JSON 数组保存在每个用户记录中。
- 授权判断混合使用角色、权限数组、页签、资源所有人、接收人和维修派工关系。
- `allPeople()` 从有效登录账户生成业务人员名单，导致没有账户的人不能作为完整业务人员存在。
- 部分页面权限只在前端隐藏，后端接口没有执行相同页签或模块权限判断。
- 维修管理能力主要由 `publisher` 角色决定，没有细分派工、复核、规则、确认、导出等权限。
- 默认测试账号和默认管理员密码存在生产安全风险。
- 停用账户、管理员重置密码时，在线会话没有在所有存储层立即失效。

## 3. 核心设计原则

### 3.1 人员与账户分离

- `personnel` 是全部在职及历史人员的主数据。
- `accounts` 只表示登录身份。
- 一个普通账户最多关联一个人员；人员可以不关联账户。
- 删除或停用账户不得删除人员档案、执照、授权、培训及历史业务记录。
- 人员离职采用状态变更，不物理删除历史数据。

### 3.2 使用稳定人员标识

- 数据库内部使用不可变的 `person_id`。
- 四类导入文件统一使用工号 `employee_no` 作为唯一业务识别源。
- `personnel.employee_no` 建立唯一约束，并按文本保存，保留前导零。
- 姓名、部门只用于显示和一致性交叉检查，禁止继续作为身份关联键。
- 工号变更通过专门的变更流程处理，不允许导入时自动创建成另一名人员。

### 3.3 RBAC 与业务资格分离

- RBAC 回答“当前账户是否可以调用这个功能”。
- 数据范围回答“当前账户可以操作哪些人员或业务资源”。
- 执照、授权、培训回答“目标人员是否符合具体任务资格”。
- 拥有放行或维修授权不等于拥有系统管理权限。
- 临时调配到某班组不自动改变账户角色或永久数据范围。

### 3.4 后端为唯一安全边界

- 菜单和按钮只根据后端返回的有效权限进行展示。
- 所有业务接口统一执行：登录状态、账户状态、功能权限、数据范围、资源状态、业务资格检查。
- 默认拒绝未明确授予的权限。

## 5. 四类 Excel 导入规范

### 5.1 人员基本信息

来源字段：

- 员工姓名、性别、年龄、员工工号
- 需求单位、部门
- 是否教员、职位、实际岗级
- 最高学历、英语等级
- 加入本企业途径、用工状态、派遣标志

规则：

- 一人一条，以员工工号更新人员主档。
- 姓名或部门与历史数据不一致时显示差异预览。
- 文件中未出现的原有人不得自动转为离职。
- 人员基本信息属于当前快照，但组织和状态变化需保留历史。

### 5.2 执照信息

来源字段：

- 新增的员工工号、是否在职、人员姓名、部门名称
- 执照号码、执照类型、执照英语等级
- 颁发日期、续签日期、有效年限、执照有效期、是否有效
- 备注、创建人、创建时间、修改人、修改时间
- 身份证号

规则：

- 必须使用新增的员工工号关联人员。
- 身份证号不进入正式数据库，不进入导入日志明文，也不用于人员匹配。
- 执照按人员、执照类型、执照号码及有效期间保留历史。
- 新文件未出现的旧执照不得物理删除，应标记待核实或由明确状态更新失效。

### 5.3 授权信息

来源字段：

- 用工状态、姓名、工号、所在部门名称
- 符合要求、执照号码、申请单位
- 项目代码、项目名称、授权类型、授权单位
- 证书号码、授权人、授权日期、授权有效期
- 培训到限日期、剩余天数、授权状态
- 授权备注、评估备注

规则：

- 以工号关联人员。
- `项目代码`作为能力项目稳定标识。2026-08-31 起授权项目名称统一由“人员与能力 → 后台设置”维护；导入不改名、不自动创建目录，详见 [授权项目后台设置](AUTHORIZATION_PROJECT_SETTINGS.md)。
- 剩余天数不作为权威存储值，应由到期日期实时计算。
- `符合要求=false`、授权无效、授权到期、培训到限分别保留明确状态。
- 授权更新采用历史版本或有效期间，不直接覆盖历史授权事实。

### 5.4 培训信息

来源字段：

- 人员姓名、人员工号、所属部门
- 课程代码、课程名称、课程版本、课程性质
- 开始时间、完成时间
- 培训结果、出席情况、合格情况
- 证书编号、签发人、签发单位、签发日期
- 数据来源、班级编号

规则：

- 以人员工号关联人员。
- 培训是历史明细，采用追加或有依据的修正，不因新文件缺失而删除。
- 课程代码和版本共同识别课程版本。
- 参加培训、培训合格和获得授权必须作为不同业务状态处理。

### 5.5 类别字典同步

导入同步识别并维护以下字典值：

- 人员：需求单位、部门、职位、实际岗级、学历、英语等级、加入途径、用工状态、派遣标志。
- 执照：执照类型、执照英语等级、执照有效状态。
- 授权：项目代码与名称、授权类型、授权单位、申请单位、授权状态、符合要求状态。
- 培训：课程代码与名称、课程版本、课程性质、培训结果、出席情况、合格情况、数据来源、签发单位。

首次出现的未知值进入待确认状态。相同代码出现不同名称时生成冲突，不得静默新增重复类别。

### 5.6 导入处理流程

1. 上传并记录文件哈希。
2. 校验文件类型、表头和必填字段。
3. 写入批次暂存区，不直接修改正式表。
4. 按工号匹配人员并执行姓名、部门一致性检查。
5. 识别新增、更新、无变化、失效候选和异常记录。
6. 识别新增字典值和代码名称冲突。
7. 展示差异预览和异常处理页面。
8. 管理员确认后在事务中生效。
9. 写入变更日志并递增主数据版本。
10. 通知下游模块刷新数据。

导入批次至少记录文件名、文件类型、上传人、上传时间、文件哈希、总行数、新增数、更新数、无变化数、异常数、未匹配人数、确认人和生效时间。

## 8. 下游读取规则

### 8.1 登录账户管理

读取人员工号、姓名、组织、正式班组、职位和用工状态；只维护用户名、账户状态、角色、数据范围和凭证。

支持从人员列表执行“开通账户”。未开通账户的人员仍然存在于人员中心和业务人员列表中。

### 8.2 车间人员安排

读取全部符合数据范围的在职人员及执照、授权、培训和风险信息；自行维护调配方案、临时泳道、支援池、目标值和调配记录。

必须区分：

- `home_team_id`：正式班组，由人员主数据中心负责。
- `scenario_lane_id`：临时调配位置，由车间人员安排负责。

### 8.3 信息传达

接收对象默认来自“在职人员中已开通且启用账户”的人员。历史接收记录继续关联 `person_id` 和账户快照。

### 8.4 维修派工

派工候选来自在职人员及业务资格结果，不要求所有候选都必须有账户；若要求本人在线报工，则额外检查其账户是否启用。

### 8.5 历史数据

业务表统一关联 `person_id`，并保留发生时的姓名、组织、班组等快照。人员改名或转组不得篡改历史业务展示口径。

### 8.6 信息传达兼容基线

RBAC 改造会替换信息传达的人员来源、身份关联和鉴权底座，但不得改变以下现有功能及权限结果：

- 管理员继续查看全部信息，包括作废信息。
- 发布者继续查看自己发布的信息和发给自己的信息。
- 接收者继续只看发给自己的信息。
- 发布、修改、删除继续要求相应权限；修改和删除还必须满足资源可见范围。
- 管理员可作废任意信息；发布者只可作废自己发布的信息；恢复仅限管理员。
- 管理员可催办任意有效信息；发布者只可催办自己发布的信息。
- 阅读回执只在当前人员是实际接收对象时产生。
- 附件继续继承信息可见范围和资源管理权限。
- 阅读统计继续保持现有管理员、发布者口径，并排除作废信息。

改造后的接收对象默认来自“在职人员中已开通且启用账户”的人员。第一阶段不把无登录账户人员加入线上信息接收对象。

现有信息、接收关系、阅读回执、收藏和附件不得因人员主数据切换而删除或重建。迁移时为历史关系补充 `person_id`，同时保留旧账户 ID 和发生时快照；未能匹配人员的历史记录进入异常清单，不阻断原有读取。

### 8.7 维修管控兼容基线

RBAC 改造会替换维修人员来源和权限判断方式，但不得改变以下现有功能及权限结果：

- 管理人员继续查看其管理范围内的维修机会；执行人员继续只看派给自己的任务。
- 新建、导入、修改、删除、派工、复核、工时规则维护、工时与架次确认、统计和导出保持现有可用范围。
- 只有维修任务树中的相关派工人员可以查看和提交对应报工。
- 放行架次仍只能由当前指定的放行人员提交。
- 非管理人员的维修统计继续只显示本人，管理人员继续查看其管理范围。
- 现有维修机会、非例行、派工、报工、工时、架次、规则和操作日志不删除、不重算。

现有“管理员，或拥有维修页签的发布者，可以管理维修任务”的规则必须做等价权限迁移：

- 现有管理员获得当前已有的全部维修管理权限。
- 现有“发布者＋维修页签”获得其原有维修管理能力。
- 现有接收者保留维修查看、本人执行和本人报工能力。
- 现有自定义页签和操作权限按账户实际配置迁移。

人员能力信息只增强派工候选、资格检查和风险提示，不得自动扩大或收回账户权限。若人员没有登录账户但业务允许其被派工，应明确显示“无登录账户”；需要本人在线报工的任务在最终派工前提示或阻止，并引导先开通账户。

### 8.8 权限迁移与双轨验证

- 新 RBAC 上线前生成逐账户的“迁移前权限—迁移后权限”对照表。
- 对菜单、接口、操作权限和数据范围分别比较，不能只比较角色名称。
- 新旧权限先双轨计算；新权限只记录差异，不立即阻断现有用户。
- 存在未解释的权限扩大或收缩时，不得切换对应模块。
- 信息传达和维修管控分别切换，禁止一次性全量替换后再排查问题。
- 菜单展示、按钮状态和直接接口调用必须得到一致的授权结果。
- 唯一允许立即改变的体验是：账户停用、离职、密码重置或凭证版本变化后，旧会话必须立即失效。

## 9. 生命周期联动

- 新增人员：创建人员档案，不自动创建账户。
- 开通账户：从人员中心选择人员，建立唯一 `person_id` 关联。
- 姓名或正式班组变化：更新当前主数据，历史业务保留快照。
- 临时调配：只影响调配方案，不自动修改账户权限。
- 停职或离职：停用账户、递增凭证版本、立即撤销全部会话，不删除历史。
- 恢复在职：人员状态恢复，账户需管理员确认后重新启用。
- 删除账户：保留人员及全部业务历史。
- 授权或培训到期：影响业务资格，不自动停用登录账户。

## 10. 安全修复前置项

在正式迁移 RBAC 前完成：

1. 删除生产启动时自动创建固定密码测试账号的逻辑。
2. 默认管理员首次初始化后不再在重启时重置密码。
3. 默认管理员密码改为部署时注入或首次启动设置。
4. 停用账户、密码重置、角色敏感变更后立即删除数据库和内存会话。
5. 每次请求校验账户状态、会话过期时间和 `credential_version`。
6. 不在 `localStorage` 保存明文密码。
7. 统一密码最小长度和复杂度规则。
8. 记录登录失败、权限拒绝、账户与角色变更审计。
9. 敏感字段按权限脱敏；身份证号不落正式库。

- 实现人员列表及完整档案页面。

### 阶段 2：账户与人员分离

- 新建或迁移 `accounts`，增加 `person_id`。

- 修复默认账户和会话安全问题。
- 保留兼容读取，确认后停止从 `users` 生成业务人员名单。

### 阶段 3：标准 RBAC 与数据范围

- 建立角色、权限、角色权限、账户角色和数据范围表。
- 将现有三种角色映射到新角色和权限。
- 实现统一 `authorize(user, permission, resource)` 服务。

- 新旧权限双轨计算并输出逐账户差异；差异未清零前不切换正式鉴权。

### 阶段 4：下游模块切换

- 车间人员安排切换到人员与能力 API。
- 维修派工切换到人员和业务资格服务。
- 信息接收对象切换到人员与启用账户关联视图。
- 工时、考勤和统计统一使用 `person_id`。
- 先切换测试环境并完成信息传达兼容回归，再单独切换维修管控。
- 每个模块都必须提供可回退到旧读取和旧鉴权路径的开关，验收稳定后再移除。

### 阶段 5：清理与上线

- 完成新旧结果对账。
- 停止写入旧的用户人员字段和 JSON 权限字段。
- 在至少一个稳定版本后删除兼容代码。
- 测试验收完成后删除现有测试人员数据，不将其作为正式基础数据保留。
- 测试数据必须按明确的测试来源标记或导入批次删除，并同步处理仅属于测试人员的账户关联、接收关系、派工关系、收藏、阅读回执和测试业务记录，禁止留下孤儿数据。
- 删除前输出目标清单、依赖数量和备份位置；不得通过姓名模糊匹配或无条件清空人员表。
- 默认管理员等平台必要账户与测试人员数据分开处理，不得随人员测试数据误删。
- 正式人员主数据仅由四类 Excel 的首次确认导入及后续受控更新形成。
- 执行备份恢复和权限回归演练。

### 数据导入

- 培训和历史授权不会因新文件缺失被删除。
- 字典新值和代码名称冲突可以审核。

### 账户与生命周期

- 无账户人员可存在于主数据和业务候选中。
- 一个普通人员不能关联多个账户。
- 停职、离职、账户停用和密码重置后旧会话立即失效。
- 删除账户不删除人员和历史业务记录。
- 正式转组与临时调配不会混淆。

### 权限矩阵

- 对每个权限验证无权限、本人、本班组、指定班组、全车间和全部范围。
- 前端隐藏和后端拒绝结果一致。
- 接口直接调用不能绕过菜单权限。
- 系统管理员与资质管理员权限相互独立。
- 临时调配不自动扩大数据范围。
- 逐账户对比新旧菜单、接口、操作和数据范围，未解释差异为零。

### 信息传达兼容回归

- 管理员、发布者、接收者的信息可见范围与改造前一致。
- 发布、修改、删除、作废、恢复和催办结果与改造前一致。
- 阅读回执只为接收对象产生，管理员旁观不会生成个人回执。
- 作废信息、阅读统计和附件鉴权结果与改造前一致。
- 历史信息、接收关系、阅读记录、收藏和附件数量对账一致。

### 维修管控兼容回归

- 现有管理员、发布者和接收者的维修入口及可执行动作与改造前一致。
- 管理人员和执行人员看到的维修机会范围与改造前一致。
- 派工、报工、放行、复核、规则维护、工时、架次、统计和导出结果一致。
- 历史维修机会、派工、报工、工时、架次和日志数量对账一致。
- 无账户人员的派工与在线报工限制符合明确业务规则。

### 测试数据清理

- 现有人员测试数据不出现在正式人员基础数据中。
- 清理操作只命中明确标记的测试来源或测试批次。
- 清理前存在可恢复备份，并输出人员及依赖数据清单。
- 清理后不存在悬空账户、接收关系、阅读回执、派工、工时或架次关联。
- 正式导入人员和平台必要账户不受测试数据清理影响。

- 信息发布、阅读回执、附件鉴权、作废恢复保持原有规则。
- 维修派工、报工、复核、工时和架次结果保持业务一致。

## 15. 工作树与原有数据保护

本 Codex 工作树的代码目录与主工作树分离，代码编辑不会直接修改主工作树中的对应文件。但 Git 工作树隔离不自动保证运行数据隔离，必须同时满足：

- 工作树内不存在指向原项目或生产环境的 `.env`。
- `DB_PATH`、`DATABASE_URL`、`UPLOAD_DIR` 未指向原项目、共享服务器或生产资源。
- 本地开发使用工作树内新建的 `data/muc.sqlite` 和 `uploads/`，或明确命名的测试数据库。
- 不在同一端口误操作已经运行的原项目服务。
- 不执行以原数据库为目标的迁移、导入、清理或初始化命令。

启动开发服务前应显示并确认实际数据库类型、数据库地址、上传目录和环境名称。若检测到生产地址或原项目路径，开发服务应拒绝启动。
