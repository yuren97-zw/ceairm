# 下一步：执行报工与正式派工边界

原方案4.2明确：执行报工选人只能修改当前可编辑草稿/工作单项，不能暗中改写正式派工。本轮仅修复原正式dispatch服务，不声称已覆盖该条的执行入口。

当前saveMaintenanceRoutineDraft在原锁内进行版本及资格核验后，调用applyMaintenanceReleaseSelection和syncMaintenanceRoutineAssignments，会更改放行或例行正式关联。saveMaintenanceNonroutineDraft主要保存文字/来源，另一个实际非例行执行保存服务调用syncMaintenanceNonroutineAssignments，也删除和新增正式关联。正式提报replaceMaintenanceAssignmentsFromEntries则同时承担工时结果的实际人员来源，不能把所有相关调用一律删除。

后续先用实际接口冻结“草稿人员与原派工不同”时的原正式关联、资格、来源快照及结果，逐个区分草稿保存、正式提报、放行选择和任务树复核。核对maintenanceCanSubmitReport、maintenanceReportPeople和个人执行列表当前如何依赖正式关联，以及原报工批次/已锁定快照的独立承载。再实现相互独立的草稿选择和正式派工，并保留原最终实际工作人员计费的合法来源。原明确范围、角色空缺、身份绑定与历史锁定继续服务端校验，不以当前选人反向授予派工管理权。

这是源码核对结果，尚未新增针对该差异的失败用例、修改服务或宣称通过。
